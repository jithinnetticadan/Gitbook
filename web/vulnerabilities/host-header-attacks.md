Used to identify which back-end component the client wants to communicate with, since multiple websites and apps can be accessed at the same IP. - Possible scenarios $ Virtual hosting - when a single web server hosts multiple websites or applications with single or different owners. $ Routing traffic via an intermediary - load balancer or reverse proxy used to route to different back-end servers hosting web apps. (CDN) - HTTP Host header attack $ If server implicitly trusts the Host header, and fails to validate, attacker may use this input to inject harmful payloads that manipulate server-side behavior. $ Attacks that inject a payload directly into the Host header are known as "Host header injection" attacks. $ Off-the-shelf web applications don't know what domain they are deployed unless specified. To generate absolute URL it might fetch the value from Host header. $ Possible Issues Web cache poisoning Business logic flaws in specific functionality Routing-based SSRF Classic server-side vulnerabilities, such as SQL injection - Test for HTTP Host header attacks/injection $ Supply an arbitrary Host header % Test what happens when you supply an arbitrary domain name via the Host header. % Either receive a error message "Invalid Host header" from the CDN/proxy or apps default/fallback to a page of a particular website. $ Check for flawed validation % Supply a non-numeric port, leave the domain name untouched, while potentially injecting a payload via the port. % Bypass validation entirely by registering an arbitrary domain name that ends with the same sequence of characters as whitelisted one % Take advantage of a less-secure subdomain that you have already compromised $ Send ambiguous requests % Inject duplicate Host headers % Supply an absolute URL - eg: "GET https://vulnerable-website.com/ HTTP/1.1" & "Host: attacker.com" (try using HTTP/HTTPS) % Add line wrapping - uncover quirky behavior by indenting HTTP headers with a space character or tab % Other techniques - Refer Request Smuggling $ Inject host override headers - X-Forwarded-Host, X-Host, X-Forwarded-Server, X-HTTP-Host-Override, Forwarded - Exploit the HTTP Host header $ Password Reset Poisoning \* Attacker manipulates a vulnerable website into generating a password reset link pointing to a domain under our control \* Construct a password reset poisoning attack % Attackers obtains the victim's email, issues a reset request. Modify this request where Host Header contains attacker URL. Now the email will be sent to the user containing our attacker domain along with the token. If user accesses the link or by AV scanner, attacker obtains the token. % Use the Host header to inject HTML into sensitive emails. \* Lab - Change the Host to attacker URL and try. \* Lab - Include a Override Headers with attacker domain. \* Lab - Host Header takes any arbitrary text. eg: Host: domain: This misconfiguration can be used to inject a HTML tag that would append the remaining string to attacker controlled URL. $ Web cache poisoning via the Host header \* Host header is reflected in the response markup without HTML-encoding, or even used directly in script imports. \* To construct a cache poisoning attack, elicit a response from the server that reflects an injected payload. \* Standalone caches the Host header in the cache key, so this approach works best on integrated, application-level caches but might work on standalone. \* Lab - Include a duplicate Host header or try any of the above techniques and observe the value reflected in one of the 'src' param. Store a XSS payload in the given path pointing to attacker server. Victim is then served the response from the cache containing the link to attacker server. $ Accessing restricted functionality \* Websites' access control features make flawed assumptions that allow to bypass restrictions by modifying the Host header. \* Lab - Modify the host header to localhost to access the admin pages. $ Accessing internal websites with virtual host brute-forcing \* Companies might host publicly accessible websites and private, internal sites on the same server. \* Attacker can access any virtual host on any server that they have access to, provided they can guess the hostnames or brute-force using Intruder $ Routing-based SSRF \* Check whether server tries to resolve a arbitrary domain mentioned in Host header using collaborator. Even if DNS response obtained modify the Host header to contain internal IP and access the admin panel. (Brute-force internal IP using intruder) \* Lab - Provide absolute URL along with the path eg: "GET https://domain.com/path HTTP/2" & Host header to contain collaborator link. Modify Host header, use intruder to find the private IP that gives access to admin panel. $ Connection state attacks \* Websites reuse connections for multiple request/response cycles with the same client. \* Encounter servers that perform validation on the first request they receive over a new connection. Bypass this validation by sending a normal request then following up with your malicious one down the same connection. Lab - Use the Group feature in Repeater Tab. Send requests in sequence using same connection where the first request will be normal & the following to contain malformed request where Host header points to private IP & provide absolute URL like previous lab eg. Make sure Connection header is set to keep-alive. $ SSRF via a malformed request line \* Proxies fail to validate the request line properly, which allow you to supply unusual, malformed input with unfortunate results \* eg: GET @private-intranet/example HTTP/1.1 \* Resulting upstream URL will be http://backend-server@private-intranet/example where backend-server would be considered as username.

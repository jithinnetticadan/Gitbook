# Cross-Site Request Forgery (CSRF)

{% hint style="info" %}
Allows an attacker to induce users to perform actions that they do not intend to perform.
{% endhint %}

&#x20;\- Impact of a CSRF attack? - attacker might gain full control over the user's account. - How does CSRF work? \* A relevant action - an action within app that the attacker has a reason to induce. This might be a privileged action. \* Cookie-based session handling - Action involves issuing one or more HTTP requests, and the app relies solely on session cookies to identify the user. \* No unpredictable request parameters - Requests that perform the action do not contain any parameters whose values the attacker cannot determine or guess. - Important Caveat - Although CSRF is described in relation to cookie-based session handling, it also arises in other contexts where the application automatically adds some user credentials to requests, such as HTTP Basic authentication and certificate-based authentication. - Construct a CSRF attack - Use CSRF PoC generator - Lab - Store a CSRF poc on a website and force the victim to access the page. - Bypassing CSRF token validation \* Validation of CSRF token depends on request method $ Apps validate the token when the request uses POST method but skips validation when GET is used. $ Lab - Change request method to GET and omit/change the csrf token parameter/value. \* Validation of CSRF token depends on token being present $ Applications validate the token when it is present but skip the validation if the token is omitted.\

In the csrf poc replace the csrf token with "hacked" & include associated cookie in - Bypassing SameSite cookie restrictions \* SameSite is a browser security mechanism that determines when a website's cookies are included in requests originating from other websites. \* Provide partial protection against a variety of cross-site attacks, including CSRF, cross-site leaks, and some CORS exploits. \* Chrome applies Lax SameSite restrictions by default if the website that issues the cookie doesn't explicitly set its own restriction level. \* Site is defined as top-level domain (TLD), usually something like .com or .net, plus one additional level of the domain name. $ Difference between a site and an origin? \* Two URLs are considered to have the same origin if they share the exact same scheme(http/https), domain name, and port. \* Two URLs are considered to have same site if they share the same scheme & tld+1. (eg: http://app.domain.com & http://test.domain.com) $ How does SameSite work? \* SameSite works by enabling browsers and website owners to limit which cross-site requests, if any, should include specific cookies. \* Strict - Browsers will not send it in any cross-site requests. \* Lax - Browsers will send the cookie in cross-site requests, only if the request uses GET method & resulted from a top-level navigation by the user, such as clicking on a link. Cookie is not included in background requests, such as those initiated by scripts, iframes, or references to images and other resources (, ) \* None - Browsers will send this cookie in all requests to the site that issued it, even those that were triggered by completely unrelated third-party sites. \* When setting cookie with SameSite=None, the website must also include Secure attribute. Otherwise, browsers will reject the cookie and it won't be set. $ Bypassing SameSite Lax restrictions using GET requests \* Servers do not validate whether they receive a GET or POST request to a given endpoint, even those that are expecting a form submission. \* Even if an ordinary GET request isn't allowed, some frameworks provide ways of overriding the method specified in the request line. \* Lab - Convert the request to GET method & generate CSRF poc, Check whether server accepts GET method.

# Platform and Version-Specific Tests

## Record Applicability First

* <pre class="language-bash" data-line-numbers><code class="lang-bash">adb shell getprop ro.build.version.release
  adb shell getprop ro.build.version.sdk
  adb shell getprop ro.build.version.security_patch
  adb shell getprop ro.build.fingerprint
  </code></pre>
* Record OEM/model, GPU/driver, WebView/browser version, bootloader/root state, target SDK, user/profile, and special-access grants.
* Check the current advisory and vendor-shipped fix/backport; Android version or a spoofed property alone is insufficient evidence.

## Permissions and User-Granted Capabilities

<table><thead><tr><th width="159">Surface</th><th>Controlled Test</th><th>Boundary / Limitation</th></tr></thead><tbody><tr><td>Runtime permissions</td><td>Deny, revoke, select approximate location, or use one-time grants where supported</td><td>Verify graceful failure and least privilege; compare declared purpose, actual collection, and disclosures.</td></tr><tr><td>Accessibility service</td><td>Enable only an approved test service with explicit user consent; inspect events/actions exposed by sensitive flows</td><td>The service's binding permission is not an ordinary silent grant to any app. Record what the user enabled and what the OS permits.</td></tr><tr><td>Notification listener</td><td>Check synthetic OTP/message previews under actual consent, device-lock, and OS restrictions</td><td>Do not assume every listener receives every sensitive notification on every Android version.</td></tr><tr><td>Autofill / keyboard</td><td>Use an approved test provider/IME; inspect field classification, origin/account association, and sensitive values</td><td>Password autofill is legitimate functionality. A user-selected provider seeing intended data is not automatically an app flaw.</td></tr><tr><td>SMS Retriever / OTP</td><td>Verify app hash/recipient flow, receiver protection, challenge/account binding, expiry and reuse</td><td>Retriever does not grant arbitrary SMS inbox access. Distinguish SMS permission, user-consent APIs, and backend OTP validation.</td></tr><tr><td>Overlay / obscured touches</td><td>Use a harmless synthetic confirmation and approved overlay app</td><td>Record required special access; distinguish overlay tapjacking from animation/task-based attacks.</td></tr><tr><td>MediaProjection / recents</td><td>With explicit capture consent, test screen/region selection, background transitions, cancellation and secure screens</td><td>User-granted capture is not itself a bypass; identify unintended data capture or violated protection. OS versions differ in consent/session rules.</td></tr><tr><td>Foreground work / standby</td><td>Inspect service type/purpose, notification, permission, collection after backgrounding or logout, and battery exemptions</td><td>Persistent work can be legitimate; correlate collection with consent and user/session state.</td></tr><tr><td>All-files / scoped storage</td><td>Grant only approved permissions and inspect actual accessible paths/MediaStore/URI grants</td><td><code>MANAGE_EXTERNAL_STORAGE</code> needs justification; it does not automatically expose all private app data.</td></tr><tr><td>VPN service</td><td>Observe an approved VPN's routing and compare TLS-protected data visibility</td><td>VPN consent permits routing, not automatic TLS decryption or bypass of app authentication.</td></tr><tr><td>Device admin / owner</td><td>Review configured policies, enrollment and app identity</td><td>Do not trigger lock/wipe or unenroll a real device. Device/profile-owner authority is distinct from legacy admin and ordinary app privileges.</td></tr><tr><td>Work/personal profiles</td><td>Test approved cross-profile links, file grants, clipboard, and chooser behavior with synthetic data</td><td>Record policies and both profiles' identities; manifest filters alone do not override enterprise policy.</td></tr><tr><td>USB / MIDI</td><td>Exercise known handlers using approved hardware and harmless inputs</td><td>Record physical access, permission prompts, device identity, and parser behavior.</td></tr><tr><td>Bluetooth / BLE / HID</td><td>Check scoped pairing, authenticated operations, application authorization, and test-device inputs</td><td>A Bluetooth-stack CVE is not an app flaw by association; radio tests must not affect nearby devices.</td></tr><tr><td>NFC</td><td>Send a controlled tag/URI to the app's declared dispatch path</td><td>Trace proximity-triggered data into links/intents and validate destination/input handling.</td></tr><tr><td>Wireless debugging</td><td>Review pairing/authentication, trusted hosts, exposure, and cleanup on the lab device</td><td>Knowing a port is not authentication. Distinguish modern paired TLS debugging from legacy exposed ADB; do not brute-force pairing codes.</td></tr></tbody></table>

* Restore grants, test providers, pairing records, profile policies, and capture/routing changes afterward.
* Use [authentication and cryptography](authentication-and-cryptography.md) for biometrics/passkeys.
